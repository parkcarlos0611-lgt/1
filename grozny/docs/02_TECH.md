# 02. 기술 설계

## 1. 엔진 선택: "Claude Code로 만든다"는 조건에서 다시 평가

Claude Code는 **텍스트 파일을 읽고 쓰고, 명령을 실행하고, 결과(테스트, 스크린샷)를 확인하는** 방식으로 일한다.
따라서 엔진은 그래픽 성능보다 아래 기준으로 골라야 한다.

| 기준 | Unity | Godot 4 | 웹 (TypeScript + Three.js) |
|---|---|---|---|
| 코드·씬이 텍스트로 관리됨 | △ 씬·프리팹이 GUID가 얽힌 YAML이라 손으로 고치면 깨지기 쉬움 | ○ `.tscn` 텍스트 씬, 읽기 쉬움 | ◎ 전부 코드 |
| Claude Code가 직접 실행·검증 | ✕ 에디터·라이선스 필요, 클라우드 컨테이너에서 실행 어려움 | △ 헤드리스 실행 가능, 렌더링 확인은 제한적 | ◎ 브라우저(Playwright)로 실행, 스크린샷, 자동 테스트 |
| 에디터 클릭 작업 의존도 | 높음 | 중간 | 없음 |
| 3D 쿼터뷰, 조명, 컷어웨이 | ◎ | ○ | ○ (Three.js로 충분) |
| Steam 출시 | ◎ | ◎ | ○ (Electron/Tauri 포장. 예: Vampire Survivors는 처음에 Phaser(JS)로 출시됨) |
| 기존 경험 | — | — | ◎ 이 저장소의 `cage/`(웹 게임 + Playwright 테스트)와 같은 작업 방식 |

### 결론 (추천)
**TypeScript + Three.js(렌더링) + 엔진과 분리된 시뮬레이션 코어**로 간다.
- "HTML5는 한계가 있다"는 우려는 주로 **수백 개의 AI, 정밀한 시야 계산, 다층 건물**에서 나온다. 이 게임은 분대 규모(아군 3~6, 적 10~40)라 웹으로 충분하다.
- 무거운 연산(시야, 경로 탐색)은 **Web Worker**로 분리하고, 필요하면 해당 모듈만 WASM(Rust)으로 교체한다.
- 시뮬레이션 코어를 렌더러와 분리해 두면, 나중에 Godot나 Unity로 옮겨야 할 때 **규칙과 데이터(JSON)는 그대로 가져갈 수 있다.**

> 재검토 시점: M2(버티컬 슬라이스) 종료 시 성능 측정 결과로 판단. 기준은 아래 5절 참고.

## 2. 아키텍처
```
┌──────────────────────────────────────────────┐
│ app/      화면 전환, 메뉴, 세이브, 설정           │
├──────────────┬───────────────────────────────┤
│ render/      │ ui/                           │
│ Three.js     │ HUD, 인벤토리, 명령 메뉴 (DOM)   │
│ 카메라·컷어웨이 │                               │
│ 시야 마스크     │                               │
├──────────────┴───────────────────────────────┤
│ sim/  ← 순수 TypeScript, DOM·Three.js 사용 금지   │
│  world (타일·층·벽 재질) · entities · wounds      │
│  ballistics · vision · sound · ai · psyche · time │
├──────────────────────────────────────────────┤
│ data/  JSON: 무기, 탄약, 부상, 아이템, 맵, 이벤트    │
└──────────────────────────────────────────────┘
```
- **고정 틱 시뮬레이션:** 20틱/초, 시드 기반 난수 → 같은 입력이면 같은 결과(재현 가능)
- 렌더러는 sim 상태를 **읽기만** 한다. 입력은 `Command` 객체로 sim에 전달
- 이 구조 덕분에 Claude Code가 **화면 없이 Node에서 전투를 1000번 돌려 밸런스를 검증**할 수 있다


## 4. 도구
| 용도 | 도구 |
|---|---|
| 언어 | TypeScript (strict) |
| 빌드·개발 서버 | Vite |
| 렌더링 | Three.js (OrthographicCamera) |
| 단위 테스트 | Vitest |
| E2E, 스크린샷 | Playwright |
| 데이터 검증 | JSON Schema (ajv) |
| 맵 제작 | 초기: 코드/JSON 직접 작성 → 이후: Tiled(.tmj) 또는 자체 에디터 |
| 3D 에셋 | Blender → glTF. 초기에는 박스·기본 도형(프로시저럴)으로 대체 |
| 배포 | 웹 데모(정적 호스팅), Steam: Electron 또는 Tauri |

## 5. 성능 목표 (M2에서 측정)
- 1080p, 내장 그래픽에서 60fps
- 동시 개체: 아군 6 + 적 40 + 민간인 20
- 맵: 128×128 타일 × 최대 5층
- 시야 계산: 개체당 틱마다 2ms 이하 (Worker)
- **이 기준을 못 맞추고 최적화로도 해결이 안 되면** Godot 4 이식을 검토한다

## 6. Claude Code 작업 방식 (CLAUDE.md에 반영)
- 티켓 하나 = 한 세션 분량. 완료 기준(테스트, 스크린샷)을 티켓에 명시
- sim 코드는 반드시 테스트와 함께 작성
- 화면 변경은 Playwright 스크린샷을 `docs/shots/`에 저장해 확인
- 밸런스 수치는 코드에 하드코딩하지 않고 `data/*.json`에 둔다

### 7.2 모바일 성능 예산 (엔진과 무관하게 적용)
| 항목 | 규칙 |
|---|---|
| 프레임 | 모바일 30fps 상한, 메뉴·일시정지·대기 화면에서는 렌더링 중단 |
| 해상도 | 렌더 배율 상한 1.5 (폰 기본 3배를 그대로 쓰지 않음) |
| 시야 | 시야 다각형은 플레이어가 움직이거나 돌 때만 다시 계산. 시야 텍스처는 1/4 해상도 |
| 조명 | 정적 조명은 미리 구워 둠. 동적 광원은 화면당 최대 4개 (화재, 총구 섬광, 조명탄) |
| 파티클 | 화면당 최대 300개. 품질 단계(낮음/중간/높음)로 조절 |
| 후처리 | 모바일 기본값: 블러, 블룸, 그레인 끔. 색 보정은 1회 패스 |
| 그리기 | 스프라이트 아틀라스 사용, 화면당 드로우콜 100회 이하 |
| 메모리 | 매 프레임 객체 생성 금지 (오브젝트 풀) |
| 백그라운드 | 탭/앱이 숨겨지면 루프 정지 |
| 측정 | 매 마일스톤마다 중급 안드로이드 기기 1대로 측정: 30분 플레이 시 배터리 소모 15% 이하, 발열로 프레임 떨어짐 없음 |
