# 검토 10 — 기자 체계와 동네 등록부 데이터베이스

기획자 지시(2026-11-19)에 대한 검토다. 아직 적용하지 않았다. 맨 끝의 결정 사항에 답을 받으면 적용한다.

같은 날 확정된 것:
- "기사 성향"은 호재·악재·중립의 논조다.
- 본문은 세 층(사실 문장, 짜임 틀 10개, 어투 10가지)으로 조합한다.
- 효과는 등록부 → 수치 변화 7가지 → 기회 4가지 순으로 넣는다.
- 현실 기사 검증은 나중에 따로 한다.

---

## 1. 기자 체계

### 1-1. 지시 내용

- 어투 10가지가 있고, 이름 있는 기자 10명이 하나씩 갖는다.
- 이름 있는 기자 10명의 이름은 게임을 시작할 때 무작위로 정해진다.
- 이름 있는 기자가 은퇴하면 이름만 바뀐 새 기자가 같은 어투로 다음 호부터 나온다.
- 이름 없는 기자들은 어투 10가지 중 하나를 무작위로 받고, 몇 달이나 몇 년마다 교체된다.

### 1-2. 구조 제안

신문사에 "자리"를 둔다. 자리는 바뀌지 않고, 앉은 사람이 바뀐다.

| 자리 | 수 | 어투 | 사람 | 이름 표기 |
|---|---|---|---|---|
| 이름 있는 기자 | 10 | 자리마다 고정(어투 1~10) | 시작할 때 무작위 이름·나이. 은퇴하면 새 사람 | 기사 끝에 이름 |
| 이름 없는 기자 | 4 (제안) | 앉을 때마다 10가지 중 무작위 | 6~30개월마다 교체 | 없음 |

```
Seat      { id, kind: named | staff, voice, beat, personId?, since, until? }
Reporter  { personId, name, born, joined, retired? }     // 이름 있는 기자만. 사람 데이터는 05 문서의 Person을 쓴다
```

### 1-3. 누가 어떤 기사를 쓰나

| 기사 | 쓰는 자리 |
|---|---|
| 가상 3~6단계 | 이름 있는 기자. 맡는 분야(관계)와 성향이 맞는 사람 중에서 고른다 |
| 가상 1~2단계 | 이름 없는 기자. 호마다 무작위 |
| 현실 기사 | 통신 기사로 싣는다(가상의 통신사 이름과 발신지). 지역 반응 문단만 이름 있는 기자가 덧붙인다 |
| 공방에 관한 기사 | 자동차 담당(어투 7) 자리 |

- 어투와 기사가 안 맞는 것을 막는다. 예를 들어 들뜬 응원가 어투(5번)는 악재 기사를 쓰지 않는다. 어투마다 쓸 수 있는 성향과 분야를 데이터에 적는다.
- 맞는 기자가 없으면 건조한 통신체(1번)가 쓴다.

### 1-4. 은퇴와 교체

| 대상 | 규칙 |
|---|---|
| 이름 있는 기자 | 시작 나이 26~62세를 고르게 흩어 놓는다. 62~70세 사이의 정해진 나이에 은퇴한다. 낮은 확률로 이직·사망도 있다 |
| 후임 | 같은 자리, 같은 어투, 새 이름, 나이 24~35세. 다음 호부터 쓴다 |
| 이름 없는 기자 | 앉을 때 임기(6~30개월)를 뽑는다. 임기가 끝나면 새 어투를 무작위로 받는다 |

- 은퇴와 부임은 신문에 실린다("본지 아무개 기자, 30년 필봉 놓는다", "새 얼굴"). 가상 기사 주제에 넣는다.
- 5년 슬라이스에서도 교체가 보이도록, 시작할 때 10명 중 2~3명은 58세 이상으로 둔다.
- 70년을 가면 자리마다 3~4대가 지나간다. 어투는 자리에 남으므로 "이 신문의 경제면은 늘 숫자투성이"라는 전통이 생긴다.

### 1-5. 검토 의견

| 항목 | 의견 |
|---|---|
| 어투가 자리에 고정되는 것 | 좋다. 플레이어가 기자의 글버릇을 알아보게 되고, 사람이 바뀌어도 신문의 성격이 유지된다 |
| 후임이 완전히 같은 어투 | 약간 단조로울 수 있다. 제안: 후임은 같은 어투에 작은 개인 버릇 1~2개(자주 쓰는 낱말, 문장 길이)를 따로 받는다. 어투는 같되 사람이 바뀐 것은 느껴진다 |
| 이름 없는 기자의 주기적 교체 | 좋다. 작은 기사들의 분위기가 시기마다 달라진다. 다만 1~2단계 기사는 1~3문장이라 어투 차이가 작게 보인다. 어투의 문장 끝맺음과 덧붙이는 한마디로만 차이를 낸다 |
| 저장 | 자리 14개와 기자 이력만 저장한다. 본문은 저장하지 않고 필요할 때 다시 만든다(같은 씨앗이면 같은 글) |
| 다른 매체 | 잡지와 뒤 단계의 큰 신문에도 같은 구조를 쓴다. 매체마다 어투 묶음이 다르다 |

## 2. 동네 등록부 데이터베이스

### 2-1. 지시 내용

동네 등록부를 데이터베이스 형태로 만들어, 일어난 일을 계속 기록하고 기억하게 한다.

### 2-2. 구조 제안

표 두 개로 만든다. 하나는 "지금 무엇이 어떤 상태인가", 하나는 "언제 무슨 일이 있었나"다.

```
Entity   { id, kind, name, status, since, attrs: { ... }, links: [entityId] }
Record   { id, date, entityId, type, from?, to?, importance, source: { issueId, articleId }?, note? }
```

| 표 | 성격 | 예 |
|---|---|---|
| 대상(Entity) | 지금의 상태. 바뀌면 덮어쓴다 | 농민저축은행: 상태 "불안", 1931-02-12부터 |
| 기록(Record) | 지나간 일. 덧붙이기만 하고 고치지 않는다 | 1931-02-12 농민저축은행 "건전 → 불안", 3단계, 제58호 기사 |

### 2-3. 대상의 종류와 상태

| 종류 | 처음 수 | 상태 | 가진 값 |
|---|---|---|---|
| 은행 | 6 | 건전 / 불안 / 인출 사태 / 문 닫음 / 합병됨 | 예금 규모, 지점장 |
| 공장 | 10 | 정상 / 단축 조업 / 감원 / 폐쇄 / 증원 | 고용 인원 |
| 경쟁 제작사 | 10 | 정상 / 어려움 / 파산 / 인수됨 | 대표 차종, 값 수준 |
| 도로 | 12 | 흙길 / 자갈 / 공사 예정 / 공사 중 / 포장 | 길이 |
| 관직 | 8 | 재임 중인 사람, 임기 끝 | 군수, 보안관 등 |
| 가게·모임 | 필요할 때 생김 | 영업 / 폐업, 주인 | |
| 이름난 사람 | 필요할 때 생김 | 생존 / 사망 | 기사에 나온 일 |
| 공급사 | 12 (이미 있음) | 등록부가 기존 공급사 데이터를 가리킨다 | |

- 상태는 정해진 길을 따라 움직인다. 은행은 "건전 → 불안 → 인출 사태 → 문 닫음"으로 가고, 불안에서 건전으로 돌아올 수도 있다. 넘어갈 확률은 경기와 지금 상태가 정한다.
- 상태가 바뀌면 그 주 신문에 기사가 나고, 기록 표에 한 줄이 쌓인다.
- 대상끼리 이어진다. 은행가 고객은 다니는 은행에, 직공 고객은 일하는 공장에 이어진다. 그 은행이 문을 닫으면 그 고객이 돈을 못 낸다.

### 2-4. 기억을 쓰는 곳

| 쓰는 곳 | 어떻게 |
|---|---|
| 모순 방지 | 문 닫은 은행, 포장된 길, 죽은 사람은 다시 그 상태의 기사가 나오지 않는다 |
| 이어지는 기사 | "지난달 감원에 이어", "3년 만에 다시 문 연" 같은 문장을 기록에서 찾아 넣는다 |
| 기념 기사 | "대화재 1년", "은행 도산 5주기" |
| 부고 | 이름난 사람이 죽으면 그 사람이 나왔던 기사를 모아 쓴다 |
| 고객 편지 | "작년에 공장이 문 닫은 뒤로"처럼 고객의 사정에 등록부의 사실이 들어간다 |
| 효과 | 상태 변화가 게임 수치를 바꾼다(검토 09의 3장) |
| 회사 연대기 | 뒤 단계에서 플레이어가 동네의 역사를 찾아볼 수 있다 |

### 2-5. 찾는 방법

데이터베이스처럼 조건으로 찾을 수 있게 한다.

| 질문 | 쓰임 |
|---|---|
| 이 대상의 지금 상태는? | 기사 조건 |
| 이 종류에서 이 상태인 대상은? | 기사 대상 고르기 |
| 이 대상에 있었던 일 전부는? | 이어지는 기사, 부고 |
| 지난 N일 동안 이 종류의 일이 있었나? | 같은 일이 너무 자주 나오지 않게 |
| 오늘과 같은 날짜에 있었던 큰일은? | 기념 기사 |

### 2-6. 크기와 저장

| 항목 | 값 |
|---|---|
| 대상 수 | 처음 약 60개, 70년 뒤 약 400개(가게, 사람이 늘어난다) |
| 기록 수 | 주 3~5건이면 70년에 약 1만 5천 건 |
| 저장 크기 | 기록 한 건 약 100바이트면 70년에 약 1.5 MB |

- 세이브 파일에 그대로 넣는다. 따로 데이터베이스 프로그램을 쓰지 않는다. 모바일과 PC에서 같은 파일로 움직이고, 같은 씨앗이면 같은 기록이 나온다.
- 크기가 문제가 되면 10년 넘은 1~2단계 기록을 "그해 요약" 한 줄로 묶는다. 3단계 이상은 계속 둔다.
- 찾기는 종류별·대상별 색인을 메모리에 만들어 쓴다. 색인은 저장하지 않고 불러올 때 다시 만든다.

### 2-7. 검토 의견

| 항목 | 의견 |
|---|---|
| 필요성 | 높다. 어색한 조합의 가장 큰 원인(상태를 기억하지 못함)을 없애고, 효과 다양화와 은행·경쟁사 시스템의 바탕이 된다 |
| 위험 | 범위가 끝없이 커질 수 있다. 종류를 은행, 공장, 경쟁사, 도로, 관직 5가지로 시작하고, 가게·사람은 기사에 처음 나올 때 만든다 |
| 기존 데이터와의 관계 | 공급사, 고객, 직원은 이미 따로 있다. 옮기지 않고 등록부가 가리키기만 한다 |
| 가상 기사 주제와의 관계 | 지금은 주제가 낱말 목록에서 은행 이름을 뽑는다. 등록부가 생기면 낱말 목록 대신 등록부에서 조건에 맞는 대상을 뽑는다. 주제 데이터에 "어떤 상태에서 어떤 상태로"를 적는다 |
| 플레이어에게 보이는가 | 처음에는 보이지 않는다(신문으로만 안다). 뒤 단계에서 스크랩북과 회사 연대기로 일부를 열어 준다 |

### 2-8. 넣는 순서

1. 표 두 개와 찾기, 저장, 시험
2. 은행·공장·경쟁사·도로·관직의 상태 길(데이터)
3. 가상 기사 주제를 등록부에 연결(낱말 목록 → 등록부 대상)
4. 이어지는 기사 문장("지난달에 이어")과 기념 기사
5. 고객과 은행·공장 연결, 효과 연결

## 3. 결정이 필요한 것

1. 기자 체계를 "자리 14개(이름 있는 10, 이름 없는 4)"로 만들지.
2. 후임 기자에게 작은 개인 버릇을 줄지, 완전히 같은 어투로 둘지.
3. 현실 기사를 통신 기사 + 지역 반응 문단으로 싣는 방식으로 갈지.
4. 등록부를 표 두 개(대상, 기록)로 세이브 파일에 넣는 방식으로 갈지.
5. 등록부를 처음에 5가지 종류(은행, 공장, 경쟁사, 도로, 관직)로 시작할지.
