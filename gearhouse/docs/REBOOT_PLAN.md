## 1. 1차 테스트판 재사용 판정 (2판)

1판 표에서 바뀐 것만 적는다. 나머지 판정(픽셀 버퍼·팔레트, 번역·폰트, 소리 합성, 이미지 요청서 이전 / 구 생성기·실측 복제 차량 폐기 / 화면 흐름 참고)은 그대로다.

| 모듈 | 1판 | 2판 | 이유 |
|---|---|---|---|
| `sim/engine.mjs`(엔진 설계값 → 토크·무게·원가·내구) | 이전 | **이전** | 프롬프트의 "이미 검증된 계산 공식" 우선 이전 후보. 표는 JSON으로 뺀다 |
| `sim/chassis.mjs`(정적 수치: 승차·롤·횡G·제동·페이드·원가) | 이전 | **이전(계산 엔진만)** | 화면 없는 계산 공식이라 이전 대상이다. 실시간 주행과는 분리한다 |
| `sim/drive.mjs`(0-60·최고속 계산, 변속기 표) | 이전 | **이전(계산 엔진만)** | 같은 이유 |
| `sim/dyn.mjs`(1 kHz 실시간 물리) | 이전 | **참고만** | 조향 불안정·보완 필요(답변 1). 2장 원인 분석의 자료로만 쓰고 새로 설계한다 |
| `game/drive3d.mjs`, `game/sideview.mjs` | 이전 | **참고만** | 탑뷰 기본으로 바뀌었다. 사이드샷 장면을 만들 때 카메라 수식(지평선 고정)과 겹 구조만 참고한다 |
| `tools/dyncheck.mjs` | 이전 | **이전(형식만)** | "설계값 대 보고서 ±10%" 자동 비교 방식과 시험 항목을 새 물리에 다시 붙인다 |
| `tools/pixel/gen/car.mjs` | 이전 | **참고만** | 25 mm/px 기준이다. 400px(약 12.5 mm/px)로 바뀌면 음영·디테일 규칙을 다시 짜야 한다. 볼륨 음영·크롬·유리 처리 방식만 가져온다 |

## 2. 1차 실시간 물리·주행의 문제와 원인 (재설계 근거)

1차 테스트판 코드와 시험 기록(계획 §23·§24)에서 확인한 원인이다.

| 증상 | 원인 | 새 설계에서 |
|---|---|---|
| 조향이 불안정하다(저속에서 휙 돌고, 고속에서 갑자기 스핀) | ① 키보드 입력이 −1/0/+1이고, 바퀴 각도가 정해진 속도로 따라가기만 했다. 핸들 복원력(캐스터·타이어 복원 토크)과 사람의 미세 조정이 없다. ② 저속 슬립각 계산(`atan(vy, │vx│+0.5)`)과 이완 길이가 적분 간격과 맞물려 저속 진동이 났다. ③ 요 감쇠가 타이어에만 의존했다 | 조향계 모델(기어비·캐스터 복원 토크·유격·조향 힘). 저속에서 슬립을 속도 기반 감쇠로 부드럽게 바꾼다. 입력 장치별 보정(키보드: 목표각 + 속도별 제한 + 자동 중심 복귀, 게임패드: 아날로그 곡선, 터치: 가상 핸들) |
| 라인 보조가 흔들리고 스핀했다 | 순수 추종·Stanley 제어를 차 한계 근처에서 썼다. 보조와 물리가 서로 싸운다 | 보조는 플레이어 입력을 다듬는 정도(카운터 보조 켜고 끄기)로만 둔다. 차를 대신 몰지 않는다 |
| 1차 주행 화면이 2D와 맞지 않았다 | 도로 좌표계(s, n, ψ)에서만 움직였다. 길을 따라가는 화면에는 맞지만 자유 주행·탑뷰에는 맞지 않는다 | 월드 좌표(x, y, 요)의 평면 강체 + 차체 상하·롤·피치 + 바퀴 4개. 길은 데이터(폭·노면·고도)로만 준다 |
| 바퀴가 튀고 헛돌다 스핀했다(험로) | 노면 진폭과 바퀴 튐 진동수가 겹쳤다. 타이어 수직 모델이 단순했다 | 노면 종류별 실측 수준 진폭, 타이어 수직 강성·감쇠, 접지 하중이 0일 때의 처리를 시험한다 |
| 경사 오벌에서 미끄러졌다 | 경사 노면의 수직 하중 증가가 처음에 없었고, 경사각이 계단처럼 바뀌었다 | 노면 법선 기준의 힘 계산 |

**재설계 원칙:**
- 계산 엔진(화면 없음)과 화면 주행이 같은 차량 모델을 쓴다(프롬프트 8장).
- 타이어는 간소화 Pacejka(마법 공식 계수 4개 + 하중 민감도 + 마찰 타원)로 한다.
- 주기는 500~1000 Hz 고정 주기에 반암시적 적분으로 한다.

**검증 시험(새 물리의 통과 기준):**
- **응답:** 계단 조향의 요 각속도 오버슈트와 정착 시간, 정상 원선회 언더스티어 기울기, 저속 원(5 m/s)에서 진동이 없을 것
- **제동:** 코너 중 제동, ABS 없는 차의 급제동 바퀴 잠김(앞이 잠기면 조향 불능)
- **거동:** 가속을 떼면 생기는 오버스티어, 논파워 조향의 조향 힘
- **보고서 대비:** 0-60, 최고속, 60-0, 횡G가 계산 엔진 보고서와 ±10% 이내

## 3. 탑뷰 주행 설계

### 3-1. 2D에서 입체감 내는 방법
1. **스프라이트 스태킹(추천):**
   - 차 설계(측면·정면·평면 실루엣과 패널)에서 높이별 단면 층을 만들고, 층을 조금씩 어긋나게 쌓아 그린다.
   - 차가 어느 각도로 돌아도 부피가 보인다.
   - 롤·피치는 층의 어긋남(위층이 바깥으로 기움)으로, 서스펜션은 차체 층 묶음과 바퀴 층 묶음의 상대 이동으로 보인다.
   - 같은 저장소의 다른 프로젝트 브랜치(`ccr-9dbda530-uh1nos`)에 전차용 시범(탑뷰 그림 + 높이맵 → 2.5D, 조명, 벽 넘을 때 피치)이 있어 참고한다.
2. **그림자:** 해 위치에 따라 차 윤곽을 땅에 비춘다. 뜨면 그림자가 떨어지고 흐려진다.
3. **노면 흔적:** 타이어 자국(미끄러질 때 진하게), 흙길 바퀴자국, 먼지·물보라·자갈 튐, 브레이크 잠김 연기
4. **카메라:** 위에서 수직으로 내려다보지 않고 약 60°로 살짝 기울인 시점에서 진행 방향을 위로 놓는다. 회전 방식은 시험 후 결정한다(돌아가는 화면은 멀미 위험이 있어 기본값을 북쪽 고정으로 할지 검증).

### 3-2. 탑뷰 차량 스프라이트 규격(제안, 결정 필요 — 질문 3)

| 항목 | 제안 |
|---|---|
| 축척 | 25 mm/px(5 m 차 = 200px 길이, 폭 약 72px). 설계 화면의 400px(12.5 mm/px)를 절반으로 줄인 단면 층에서 만든다 |
| 층 수 | 높이 1.5 m를 약 24~30층(층당 2px) |
| 방향 | 실시간 스태킹(각도 자유). 느린 기기를 위해 64방향 미리 굽기 선택 |
| 화면 | 주행 장면은 한 화면 픽셀 = 2 실제 화소(1080p 기준), 도로 폭 7 m = 280 실제 화소 |

### 3-3. 사이드샷을 쓰는 장면
- 시험장 직선(가속·최고속·제동 계측)
- 언덕 오르기
- 잡지 사진 촬영
- 출시 행사

1차 테스트판 사이드샷의 카메라 수식(지평선 고정, 실제 비례)을 참고한다.

## 4. 그래픽 규격

1. **에셋 규격과 화면 규격을 분리한다(프롬프트 8장).**
2. **차량·부품 에셋:**
   - 차량은 약 400px(측면 길이 기준, 약 12.5 mm/px)로 그린다. 이 규격은 설계·잡지·전시 화면용이다.
   - 엔진·변속기 같은 큰 부품도 같은 축척으로, 볼트·이음새·크롬·도장 질감이 보이는 밀도로 그린다.
3. **장면 픽셀 크기:**
   - 한 장면 안에서는 픽셀 크기가 하나다.
   - 1080p 기준으로 장면 1픽셀 = 화면 2화소다. 400px 차는 화면에서 800화소로, 폭의 42%를 차지한다.
   - 기기별 배율은 정수만 쓴다(1080p ×2, 1440p ×2·×3, 4K ×4, 휴대폰은 화면 높이에 맞는 정수).
4. **화면 비율:** 16:9를 기준으로 하고, 16:10·4:3·휴대폰 가로(19.5:9)에서는 늘어난 쪽으로 장면을 더 보여 준다. 레터박스는 쓰지 않는다. UI는 안전 영역(노치) 안에 둔다.
5. **배경·장소:**
   - 시대 사진·지도·건축 자료를 참고해 정확도를 높인다.
   - 에셋마다 `docs/asset_sources.md`에 참고 출처를 기록한다.
   - 공공 자료(예: 미국 의회도서관, 위키미디어 공용의 저작권 만료 사진)를 우선 쓴다.
6. **제작 방식(결정 필요 — 질문 2):**
   - 차량·부품: 설계 데이터에서 절차 생성하고, 손질 규칙은 코드로 둔다.
   - 배경·소품: 기획자가 생성한 이미지 → 처리 도구(배경 빼기, 축척, 시대 팔레트로 색 줄이기, 접지선) → 필요하면 손 보정
   - 초상화: 부위 조합

## 5. 기술 스택

| 영역 | 후보 비교 | 제안 |
|---|---|---|
| 렌더링 | **PixiJS 8:** WebGL2/WebGPU 렌더러만 있다. 장면·UI·물리 구조를 우리가 정한다. 배치 그리기·필터·렌더 텍스처가 강하다. **Phaser 3:** 장면·입력·물리·트윈까지 있는 프레임워크다. 우리 코어(결정론 시뮬레이션·자체 물리)와 겹치는 부분이 많다 | **PixiJS 8.** 시뮬레이션 코어와 UI 구조를 직접 갖는 게임이라 렌더러만 쓰는 쪽이 맞다 |
| 모바일 포장 | Capacitor(iOS WKWebView, Android WebView) | Capacitor |
| PC·Steam 포장 | **Electron:** 모든 OS에서 같은 Chromium. Steamworks 연동 라이브러리(steamworks.js)가 있다. 용량 100 MB 이상. **Tauri 2:** 가볍지만 OS별 웹뷰가 다르다(맥 WKWebView, 윈도 WebView2). 그래서 렌더 차이를 OS마다 따로 시험해야 한다 | **Electron.** Steam 연동과 렌더 일관성 |
| 빌드·시험 | Vite, Vitest(단위 시험), Playwright(화면 비율별 자동 스크린샷) | 그대로 |
| 개발 중 미리보기 | 게임 페이지(아티팩트, 16 MB 한도) | 단계마다 휴대폰으로 확인 |

**위험:** iOS 웹뷰의 WebGL 성능과 메모리 한도가 있다. 400px 에셋과 스프라이트 스태킹을 쓰려면 텍스처 아틀라스와 동적 해제가 필요하다. 프로토타입 ④에서 실제 아이폰 성능을 확인해야 한다.

## 6. UI 품질 기준 실행 방법

1. **공통 컴포넌트(버튼·목록·창·글 상자)에 규칙을 넣는다.**
   - 최소 누름 영역 44pt/48dp
   - 즉시 반응, 늦어지면 로딩 표시
   - 자동 줄바꿈·말줄임
   - 창 관리자: 모달 하나, 앞뒤 순서, 화면 밖으로 나가지 않기, 닫기 버튼 항상 표시
2. **자동 검사(1차 테스트판 버튼 점검 방식 확장):**
   - 모든 화면을 한국어·영어로 각각 16:9, 16:10, 휴대폰 가로, 4:3에서 스크린샷을 찍는다.
   - 다음을 자동 판정한다: 글자가 칸을 넘는 곳, 창이 겹쳐 가려진 버튼, 누름 영역이 기준보다 작은 것, 반응이 없는 버튼.
   - 화면 완료 보고에 이 결과를 붙인다.
3. **입력:** 마우스·터치 동시 대응, 손가락 여러 개, 게임패드(주행)

## 8. 남은 모순·위험

| 순위 | 항목 | 대응 |
|---|---|---|
