## 2. 도면 화면은 어디까지 왔나

| 항목 | 상태 |
|---|---|
| 입체 모델에서 선 도면(옆·위), 1px 선 | 됨 |
| 빨간 수정선 → 수정(지우개) / 취소, 연필 소리 | 됨 |
| 도면 4종(닳은·깔끔한 제도지, 청사진, 검은 화면 주사선) | 됨 |
| 치수 키보드 입력 | 됨 |
| 고정점·묶음: 앞문 길이, 6라이트↔4라이트↔2도어 자동 제안 | 됨 (1929 세단) |
| 램프 앞뒤·높이, 그릴 앞뒤·크기, 범퍼 유무·크기, 펜더 유무·크기 | 됨 |
| 시대 × 회사 규모 조절표 | 됨 (값은 1차 추정) |
| 주문서 체크리스트, 견적, 외장 미리보기 | 됨 (값은 1차 추정) |
| 게임 상태(주문, 회사 규모, 날짜)와 연결 | **안 됨** — 데모 안의 고정 값 |
| 다른 차종(로드스터, 트럭)의 고정점 | 안 됨 |
| 부품표 → 공급사 주문 → 제작 공정 연결 | 안 됨 |

즉 도면 화면은 **"기능 시제품"(무엇을 해야 하는지 보여 주는 견본) 단계**다. 기능은 대부분 확인됐고, 게임 부품으로는 아직 아니다.

## 3. 판단: 데모에 계속 붙여서 게임을 만들면 비효율인가

**맞다. 지금 방식으로 데모 파일에 기능을 계속 붙이면 낭비가 커진다.** 이유:

1. 데모는 화면 좌표를 손으로 박아 둔 한 파일(약 400줄)이다. 버튼이 늘 때마다 자리를 다시 맞추고, 같은 황동 버튼·탭·숫자 창을 화면마다 다시 짠다.
2. 데모는 게임 상태(core/의 GameState, 주문, 회사 규모, 날짜)를 모른다. 주문서도 회사 규모도 데모 안에 박혀 있다. 나중에 잇는 비용이 기능을 늘릴수록 커진다.
3. 데모마다 따로 묶어 따로 배포한다(도면, 시험 주행장, 책상). 화면 사이 이동, 저장, 소리 같은 공통 기반이 없다.
4. 확인은 매번 눈으로 스크린샷을 본다. UI 자동 검사(계획 ⑤)가 없다.

**그러나 버릴 것은 적다.** 다시 쓸 수 있는 핵심은 이미 모듈로 나뉘어 있다:
- core/* (경영 시뮬레이션 전체, 96개 테스트)
- render/car/* (입체 부품 모델, 픽셀 그림)
- ui/drawing/lines.ts (선 도면, 편집 엔진), ui/drawing/rules.ts (조절표)
- physics/* (주행 장치)
- ui/pixel/screen.ts (픽셀 버퍼, 글꼴)

버려야 할 것은 데모의 "껍데기"(손으로 박은 배치, 데모 전용 상태)뿐이다.

## 4. 추천: 기능 추가를 멈추고 "통합 단계"를 먼저

| 순서 | 할 일 | 결과 |
|---|---|---|
| 1 | **픽셀 UI 공통 부품 한 벌**: 판(9조각), 황동 버튼, 탭(눌린 상태 유지), 숫자 창(키보드 입력), 토글, 목록, 카드, 스크롤. 배치는 좌표 대신 행·열 레이아웃 | 화면 하나 만드는 비용이 크게 준다 |
| 2 | **게임 껍데기**: 화면 관리자(화면 쌓기, 이동, 뒤로), 한 개의 진입점(game.html), 소리 관리자, 저장 연결 | 모든 화면이 한 게임 안에서 움직인다 |
| 3 | **UI 자동 검사**(Playwright): 4가지 화면 비율에서 글자 넘침, 겹침, 누름 영역 | 스크린샷 눈 확인을 줄인다 |
| 4 | **도면 화면을 게임 화면으로 옮기기**: core의 주문(요구서)·회사 규모·날짜를 읽고, 결과(설계안)를 GameState에 저장 | 첫 "차 만드는 쪽" 연결 |
| 5 | **책상 화면을 픽셀로** 다시 만들고, 책상 → 주문 → 도면 → 견적 → 제작 → 시험 → 인도 한 바퀴 | 세로 조각의 뼈대 완성 |
| 6 | 그 뒤에 기능을 넓힌다: 계산 물리 ②, 엔진 사다리(검토 31), 다른 차종 고정점, 부품표 → 공급사 | 기능은 껍데기 위에 붙인다 |

1~4는 대략 데모 하나 만든 것과 비슷한 양이다. 그 뒤로 화면을 하나 더할 때마다 드는 비용이 줄어든다.
