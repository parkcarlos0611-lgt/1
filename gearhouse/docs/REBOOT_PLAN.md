## 0. 아이디어 구성안과 프롬프트 대조

프롬프트는 구성안을 거의 빠짐없이 옮겼고, 경제·경쟁사·재무·개인 생활·튜토리얼(10장)을 더해 연결성을 보강했다. 둘 사이에 다른 점은 세 가지다.

| 항목 | 구성안 | 프롬프트 | 판단 |
|---|---|---|---|
| 그래픽 규격 | "이전보다 훨씬 많은 픽셀수, PC 게임 수준" | 내부 해상도 640×360 | **충돌.** 1차 테스트판 UI가 480×270, 사이드샷 주행 장면이 이미 960×540이다. 640×360은 UI 대비 1.33배에 그치고 주행 장면보다 작다. → 3-2에서 960×540을 제안한다 |
| 시작 규모의 운영 | 수리업체는 "자동차 진출"을 시도하는 정비소 | 수리 매출로 버티며 자체 차 개발 | 수리 업무 자체의 게임 규칙이 어디에도 없다 → 2-3 |
| 엔진 | 지정 없음 | Godot 4 기본 제안, 단 "1차 테스트판 스택 확인 후 유지/교체 비교" | 1차 테스트판은 순수 JavaScript(브라우저)다 → 3-1에서 비교한다 |

## 2. 모순·불명확·기술 위험

### 2-1. 모순

1. **그래픽 해상도:** 0장 표에 정리했다. 제안은 3-2에 있다.
2. **소규모 공방 "프레임부터 전부 직접":**
   - 1930년대 소규모 코치빌더는 대부분 완성 섀시(롤링 섀시)를 사서 차체만 얹었다. 프레임부터 직접 만드는 것은 소수의 스포츠·레이싱 공방이었다.
   - **제안:** 두 길을 모두 둔다.
     - 롤링 섀시 구매(쉬움, 차체·마감에 집중)
     - 섀시 자작(어려움, 기술 해금 필요)
   - 이렇게 해도 "직접 설계" 원칙은 깨지지 않고 난이도가 자연스럽게 생긴다.
3. **"충돌 물리학까지 전부"와 2D 측면 시점:**
   - 측면 시점에서는 충돌 상대가 앞뒤 차, 벽, 장애물뿐이다.
   - 프롬프트대로 패널 손상 영역 + 변형 단계 그림 + 부품 고장 계산으로 시작한다. 완전 변형 물리는 마지막 목표로 둔다.
   - 1차 목표에는 충돌을 넣지 않는다.
4. **"실존 브랜드는 대체, 역사적 사건은 실제":**
   - 신문에 실제 사건(대공황·전쟁)은 나오지만 실제 회사 이름은 나오지 않으므로, 경쟁사는 가상 회사다.
   - 실제 인물(정치인 등)을 기사에 이름으로 쓸지 정해야 한다. 질문 7에서 묻는다.

### 2-2. 불명확

1. **수리업체 시작의 '수리 업무' 규칙이 없다.** 손님 차 입고 → 진단 → 부품 → 수리 시간 → 청구로 이어지는 짧은 순환이 필요하다. 이 순환은 '품질·고장·리콜'(10장)과 연결된다. 내 차가 고장 나 다른 수리점에 오면 평판이 떨어지는 식이다. 1차 목표(소규모 공방)에는 필요 없으므로 3단계로 미룬다.
2. **'대기업 시작'의 플레이 방식:** "결정만 하기"의 구체 화면이 없다. 이사회 안건, 부서장 보고서, 예산 배분 등이다. 4단계에서 설계한다.
3. **"하루 단위"와 주행·제작 같은 실시간 장면의 관계:** 시험 주행 중에 날짜가 가는지 정해야 한다.
   - **제안:** 실시간 장면에 들어가면 달력을 멈춘다. 장면이 끝나면 그 장면이 쓴 시간(예: 시험 주행 반나절)만큼 진행한다.
4. **2세 상속과 가족:**
   - 결혼·자녀 시스템(10장 '개인 생활')이 필수로 올라 있지만 1차 목표에는 없다.
   - 1930~1935년 슬라이스에서는 창업자가 죽을 확률이 매우 낮다. 그래서 승계는 4단계로 미뤄도 1차 목표 판정에 영향이 없다.
5. **수명 분포:**
   - Beta(5,3)을 49~99세로 바꾸면 평균 약 80세, 최빈값 약 82세다.
   - 1930년 창업자가 30~40세라면 1975~1990년 무렵 한 번 승계한다.
   - 다만 1930년 출생 코호트의 실제 평균 수명은 이보다 훨씬 짧다. 의도한 '게임적 수명'인지 확인이 필요하다(질문 8).
6. **신문 기사 생성:** 역사적 사건(고정)과 랜덤·동적 기사의 비율, 그리고 문장을 어떻게 만들지(템플릿 조합인지 직접 쓴 기사인지)가 정해지지 않았다.
   - **제안:** 고정 기사는 직접 쓴 텍스트 데이터로 둔다. 동적 기사는 문장 틀(템플릿)에 회사·차·수치를 끼워 넣고 문장 변형 여러 벌을 둔다.

### 2-3. 기술 위험 (먼저 검증할 순서)

| 순위 | 위험 | 왜 위험한가 | 검증 방법 |
|---|---|---|---|
| 1 | 자유 편집 차체 → 고품질 픽셀아트 자동 변환 | 손으로 찍은 픽셀아트 수준이 안 나오면 게임의 매력(구성안 '그래픽')이 무너진다 | 프로토타입 ①(4장) |

## 3. 엔진·언어·폴더·데이터 형식 제안

### 3-1. 엔진 비교 (결정 필요 — 질문 1)

| | A. TypeScript + 웹 기술(추천) | B. Godot 4 (프롬프트 기본 제안) |
|---|---|---|
| 1차 테스트판 코드 이전 | 그대로 옮긴다(JS → TS). 물리·엔진 계산·픽셀 생성·소리 합성을 바로 쓴다 | 물리·계산·생성기·소리를 GDScript/C#으로 전부 다시 쓴다. 검증도 다시 해야 한다 |
| 렌더링 | WebGL2(PixiJS 8 또는 Desert Steel식 자체 배치 렌더러). 정수배 픽셀 퍼펙트는 직접 맞춘다 | 2D 픽셀 퍼펙트·조명·셰이더 내장, 에디터로 장면 배치 |
| 헤드리스 시뮬레이션·자동 시험 | node로 바로 돌린다(지금 dyncheck처럼) | `godot --headless` 가능. 이 클라우드 환경에서는 설치·화면 캡처가 더 번거롭다 |
| 개발 중 미리보기 | 지금처럼 게임 페이지(아티팩트)로 휴대폰에서 바로 플레이 | 웹 내보내기가 약 35~40 MB라 게임 페이지 한도(16 MB)를 넘는다 |
| PC·Steam 출시 | Tauri 또는 Electron으로 포장(Steam에 사례 다수) | 내보내기 기능 내장, 성능 유리 |
| 위험 | 대규모 장면 성능을 직접 관리해야 한다 | 이전 비용이 크고, 이전하는 동안 기존 검증이 끊긴다 |

- **추천:** A다. 이유는 세 가지다.
  - 가장 가치가 큰 자산이 검증된 계산 코드인데, 이것을 옮기는 비용이 0에 가깝다.
  - 프롬프트 11장의 "화면 없이 실행"이 node에서 바로 된다.
  - 휴대폰 미리보기로 기획자가 매 단계 확인할 수 있다.
- **바꿀 시점:** 출시 플랫폼(질문 2)이 콘솔이면 B가 유리해진다.

### 3-2. 그래픽 규격 (결정 필요 — 질문 4)

| 안 | 내부 해상도 | 정수배 출력 | 픽셀 밀도 |
|---|---|---|---|
| 프롬프트 안 | 640×360 | 1080p ×3, 1440p ×4, 4K ×6 | 차 200 px이면 화면 폭의 31% |
| **추천 안** | **960×540** | 1080p ×2, 4K ×4. 1440p는 ×2 + 테두리, 또는 ×2.67 근사 | 차 200 px(25 mm/px, 1차 테스트판과 같음)이면 화면 폭의 21%. 실내·소품 밀도가 2.25배 |

- **추천 이유:** 구성안의 "훨씬 많은 픽셀수, PC 게임 수준"에 맞는 쪽은 960×540이다. 사이드샷 주행이 이미 이 규격으로 돌고 있다.
- **단점:** 1440p 모니터에서 정수배가 안 된다.
- **공통 규칙:** 어느 안이든 픽셀 크기를 섞지 않는다. 시대 팔레트는 데이터로 둔다.

### 3-3. 폴더 구조 (프롬프트 11장 + TypeScript)

```
/core      시뮬레이션: 달력·틱, 이벤트 버스, 회사·인물·경제·미디어 상태(화면 코드 없음, node 실행)
/physics   계산 엔진(성능 수치) + 실시간 주행(1 kHz) — sim/dyn·engine·chassis·drive 이전
/render    WebGL 렌더러, 카메라, 장면(사무실·차고·공장·주행), 픽셀 생성기(pix·color·car 이전)
/ui        시대 소품형 UI(서류·장부·신문·전화번호부), 입력
/data      JSON: 부품·기술·사건·신문·잡지·이름·국가·팔레트·트랙 (+ JSON Schema)
/assets    픽셀아트(처리된 게임용), 사운드
/tools     이미지 처리(사용자 이미지 → 팔레트 픽셀), 폰트 굽기, 데이터 검사
/tests     물리 회귀(dyncheck 이전), 원가·경제 공식, "10년 자동 진행"
/docs      decisions.md, backlog.md, music_license.md, 이미지 요청서
/legacy    1차 테스트판(GEARHOUSE) 그대로
```

### 3-4. 데이터·코어 규칙

| 항목 | 형식 | 이유 |
|---|---|---|
| 게임 데이터 | JSON + JSON Schema 검사(시험에 포함) | 시대 파트를 추가할 때 데이터만 늘리면 된다(모드 대비) |
| 진행 | 하루 단위 틱. 같은 시드면 같은 결과 | 건너뛰기, 자동 시험, 밸런스 조정 |
| 난수 | 시드 난수 하나(예: PCG32)를 코어에 둔다. `Math.random` 사용 금지 | 1차 테스트판에서는 18곳이 `Math.random`을 썼다. 결정론의 적이다 |
| 시스템 연결 | 타입이 있는 이벤트 버스(예: `design_finalized`, `review_published`, `employee_hired`, `economy_changed`) | 직접 호출을 금지한다. 9장 연결 맵의 화살표 하나 = 이벤트 하나 이상 |
| 저장 | 버전 번호가 붙은 JSON, 구버전 변환 함수 사슬, 자동 저장 | 장기 개발 중에도 세이브가 안 깨지게 한다 |
| 문자열 | 번역 파일(한국어 우선, 영어 대비) | 1차 테스트판 i18n 이전 |
